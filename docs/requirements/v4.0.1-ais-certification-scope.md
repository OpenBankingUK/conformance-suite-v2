# v4.0.1 AIS certification scope

Open Banking Read/Write v4.0.1 AIS is the first certifiable target. This document defines the planning boundary for moving from partial suite rails to a complete certification suite.

## Target suite

| Field | Value |
| --- | --- |
| Standard | `ob-read-write` |
| Spec version | `v4.0.1` |
| API family | `ais` |
| Profile | `fapi1-advanced` |
| Suite | `ais-certification-baseline` |
| Manifest | `conformance/suites/ob-read-write-v4.0.1-fapi1-advanced-ais-certification-baseline.json` |
| Current coverage | `partial` |

## Current planning baseline

- v4.0.1 AIS baseline manifest exists and has setup, mandatory-default, and optional rows.
- A generated prior-FCS AIS inventory exists with 95 rows derived from the bundled v4 source.
- Current prior-FCS inventory counts: 24 mandatory, 34 optional, 37 conditional.
- Current mandatory parity status: 7 require v4.0.1 confirmation, 8 require new primitives, 9 are not started.
- Current v4 AIS benchmark implements 19 of the 95 prior-FCS rows, but those implementations still require v4.0.1 applicability review.

## Scope principles

- Prior-FCS parity is the baseline; Standards additions can extend it but should not hide parity gaps.
- Basic/detail and other permission/content variants must be represented explicitly.
- Negative permission, no-token, client-credentials-token, schema, and assertion-group behaviours must be implemented or explicitly waived before a complete certification claim.
- Optional and conditional tests should be selectable in the UI, not silently omitted.
- The suite remains `partial` until all promotion-gate evidence is present.

## Work packages

### 1. Standards mandatory matrix

Outcome: a Standards-owned mandatory matrix is represented in the target coverage ledger.

Deliverables:

- mandatory/optional/conditional classification for v4.0.1 AIS
- sign-off representation for waivers and legacy issues
- mapping to prior-FCS rows where applicable
- mapping to new v2 requirements where prior-FCS coverage is insufficient

### 2. Prior-FCS parity review

Outcome: every generated inventory row has a v4.0.1 decision.

Deliverables:

- `v401Applicability` reviewed for all 95 prior-FCS rows
- mandatory rows classified as implemented, waived, legacy issue, superseded, blocked, or requiring new primitive
- optional/conditional rows grouped for visual plan selection
- v4 benchmark implementations confirmed, adapted, or rejected for v4.0.1

### 3. Missing primitive implementation backlog

Outcome: uncovered mandatory behaviours become agent-ready implementation slices.

Likely primitives:

- assertion groups / `asserts_one_of`
- broader schema-check mapping
- Goessner-style or equivalent generic array predicates
- FAPI interaction ID playback assertions
- negative permission flows with dedicated auth bundles
- no-token and client-credentials protected-resource variants
- reusable legacy assertion mapping

### 4. Manifest and auth-bundle completion

Outcome: the v4.0.1 AIS suite manifest represents all mandatory coverage.

Deliverables:

- v2 steps for all mandatory endpoint/content/auth variants
- setup/auth steps for each required permission profile
- selected-step-to-auth-bundle mapping
- optional/conditional rows present and deselected by default where appropriate
- no hardcoded Open Banking policy in executor branches unless the primitive is generic

### 5. Validator and report completion

Outcome: certification can be recomputed independently by OBL.

Deliverables:

- participant result JSON carries sufficient suite, plan, coverage, custom-value, and mandatory evidence
- validator rejects partial coverage, missing mandatory rows, failed/skipped mandatory rows, unapproved tool versions, and unapproved custom values
- validator accepts only complete, approved, mandatory-passing reports

### 6. Participant and operator documentation

Outcome: participants and OBL operators can run and validate the certifiable target safely.

Deliverables:

- participant setup/config guide for v4.0.1 AIS
- guided UI instructions
- auth-method and certificate guidance
- OBL certification validator runbook
- waiver/sign-off handling guidance

## Complete-suite readiness checklist

The manifest can be changed to `certificationCoverage: complete` only when:

1. Standards mandatory matrix is recorded and signed off.
2. Every mandatory prior-FCS row has a non-blocking final status.
3. Every Standards mandatory row maps to executable v2 step coverage.
4. Missing primitives are implemented or waived.
5. Auth/content variants are represented in plan metadata and execution.
6. Tests cover parser, executor, plan builder, API/UI, result, masking, and validator behaviours affected by the suite.
7. OBL-side validator rejects all incomplete/partial/custom-invalid cases.
8. Docs and examples are aligned.
9. Release readiness items relevant to certification artefacts are complete.

## Current blockers

- `OPEN-001`: exact Standards-owned mandatory matrix.
- `OPEN-002`: repo-visible Standards sign-off/waiver representation.
- `OPEN-003`: custom-value certification policy.
- `OPEN-004`: environment capability metadata for guided auth selection.
- `OPEN-005`: headless PSU feasibility.
- Missing primitive backlog from prior-FCS parity review.

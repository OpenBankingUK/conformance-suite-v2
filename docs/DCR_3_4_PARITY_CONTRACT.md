# Open Banking DCR 3.4 Parity Contract

This document fixes the coverage and migration contract for first-class Open
Banking UK Dynamic Client Registration (DCR) 3.4 support. The machine-readable
source of truth is
[`conformance/standards/ob_dcr/v3_4/parity-contract.json`](../conformance/standards/ob_dcr/v3_4/parity-contract.json).
Later catalogue and runtime work must consume that contract rather than
reconstructing the legacy suite from counts.

[`OpenBankingUK/conformance-dcr` v1.4.0 at `cc00a0065494e8e180c915621b9996bc2259ec8d`](https://github.com/OpenBankingUK/conformance-dcr/tree/cc00a0065494e8e180c915621b9996bc2259ec8d).

and supplies 3.4 response rules in

The full-selection inventory is exactly **10 scenarios, 34 cases, and 79

The typed execution adapter now supplies discovery, JOSE, DN, mTLS, token-auth,
scenario-state, cleanup, dependency-skip, and masking primitives through shared

certification, and operational verification surfaces use that same adapter.

The JSON ledger records every case name and every hierarchical
`DCR-nnn-Cnn-Snn` step ID, along with its legacy builder operation, request
shape, status, state inputs/outputs, prerequisites, endpoint gates, source
symbol, and normative references. Case and step ordinals are stable
traceability identifiers; they are not participant-selectable tests.

## Request and state contract

- Registration is an mTLS `POST` to the discovery
  `registration_endpoint`. Its body is raw compact PS256 JWS using the
  configured `kid`, and its content type is `application/jose`. Success is
  `201`; invalid registration is `400`.
- The client-credentials dependency is an mTLS, form-encoded `POST` to the
  discovery `token_endpoint` and expects `200`. It is generated by the plan,
  not selected as a DCR endpoint.
- Management calls use
  `registration_endpoint + "/" + client_id`, mTLS, and the client-credentials
  bearer token. GET and PUT expect `200`, DELETE expects `204`, and access to an
  invalid or deleted client expects `401`.
- Scenario-local client ID, client secret, registration access token,
  client-credentials token, signed JOSE, and responses are never shared into a
  different scenario. Cases inside a scenario run sequentially.
- A failed or skipped prerequisite explicitly skips every dependent case and
  step. Cleanup is deterministic and best-effort, but cannot replace or hide
  the scenario outcome.

Executable token endpoint authentication methods are `tls_client_auth`,
`private_key_jwt`, `client_secret_jwt`, and `client_secret_basic`.
`client_secret_post` is rejected because accepting a method that the runner
cannot execute would produce a false capability claim.

## Canonical plan contract

DCR uses canonical `schemaVersion: "1.0"` with:

- scheme `open-banking-uk` (**Open Banking**);
- specification `dynamic-client-registration` (**Dynamic Client
  Registration**);
- family `OBL_DCR`;
- version `3.4` only;
- top-level `endpoints`, with no `resourceGroups`;
- mandatory, checked, locked POST registration;
- optional participant-selected GET, PUT, and DELETE management operations;
- token setup represented only as a generated dependency.

The complete proposed example is in the machine-readable contract. Its scope
shape is:

```json
{
  "schemaVersion": "1.0",
  "specification": {
    "family": "OBL_DCR",
    "scheme": "open-banking-uk",
    "name": "dynamic-client-registration",
    "version": "3.4"
  },
  "endpoints": [
    {"method": "POST", "path": "/register", "required": true, "locked": true},
    {"method": "GET", "path": "/register/{ClientId}", "required": false, "locked": false},
    {"method": "PUT", "path": "/register/{ClientId}", "required": false, "locked": false},
    {"method": "DELETE", "path": "/register/{ClientId}", "required": false, "locked": false}
  ]
}
```

No direct import of a legacy `conformance-dcr` configuration is required or
supported. Migration maps concepts into a newly validated canonical document.

## Participant and operator workflow

Select **Open Banking UK → Dynamic Client Registration → 3.4** in the browser,
or provide the same canonical document to:

```bash
uv run python main.py --test-plan /absolute/path/dcr-plan.json
curl --fail-with-body -H 'Content-Type: application/json' \
  --data-binary @/absolute/path/dcr-plan.json \
  http://127.0.0.1:8443/api/runs/
```

The REST API is loopback-only by default. DCR file references name files already
provisioned inside the running host/container; the API never accepts inline PEM,
SSA, client-secret, registration-token, grant-token, assertion, authorization,
or token-response material.

Required shared configuration:

- `securityEnvironment.discoveryUrl`;
- `securityEnvironment.clientAuthMethod`;
- `securityEnvironment.signingPrivateKeyPath` and `signingKeyId`;
- `securityEnvironment.mtls.certificatePath` and `privateKeyPath`.

`securityEnvironment.mtls.caBundlePath` and
`clientAuthSigningAlgorithm` are optional. The required DCR-owned fields are
`dynamicClientRegistration.softwareStatementAssertionPath` and
`dynamicClientRegistration.registrationAudience`. Issuer, redirect URI,
signing-certificate, transport subject-DN, numeric-OID, and disable-keepalive
values are optional explicit overrides; derivation is preferred.
Every path is absolute and must reference an existing local file before launch.

Endpoint combinations are POST alone or POST plus any combination of GET, PUT,
and DELETE. POST cannot be unchecked. GET/PUT/DELETE gates are independent, but
scenarios requiring multiple management methods run only when all prerequisites
are selected. OAuth token calls are generated dependencies and do not appear as
scope choices.

Browser safe export, review, run snapshots, REST responses, result/log downloads,
and certification artifacts preserve file references and traceability but never
file contents or generated credentials. Imported canonical documents round-trip
through the same review/export contract. A safe export with emptied secret
runtime values may require local references to be restored before relaunch.
Legacy `conformance-dcr` JSON is intentionally rejected rather than heuristically
translated; use the mapping below to create a canonical plan.

## Configuration migration

Reusable fields keep the same canonical meaning as other specifications.
DCR-only values live under `dynamicClientRegistration`.

| Legacy field/concept | Canonical location | Decision |
| --- | --- | --- |
| `spec_version` | `specification.version` | Must be `3.4` |
| `wellknown_endpoint` | `securityEnvironment.discoveryUrl` | Reuse global discovery |
| `kid` | `securityEnvironment.signingKeyId` | Reuse global signing metadata |
| `private_key` | `securityEnvironment.signingPrivateKeyPath` | File reference; never inline |
| `transport_cert` | `securityEnvironment.mtls.certificatePath` | Reuse global mTLS material |
| `transport_key` | `securityEnvironment.mtls.privateKeyPath` | File reference; never inline |
| `transport_root_cas` | `securityEnvironment.mtls.caBundlePath` | Convert the PEM array to a bundle reference |
| Discovery auth methods/algorithms | `securityEnvironment.clientAuthMethod` / `clientAuthSigningAlgorithm` | Select an advertised executable method |
| `brand`, `environment` | `metadata.brandName`, `metadata.environmentName` | Reuse reporting metadata |
| `get_implemented`, `put_implemented`, `delete_implemented` | Top-level endpoint selections | Replace booleans with shared endpoint scope |
| `ssa` | `dynamicClientRegistration.softwareStatementAssertionPath` | Sensitive file reference |
| `aud` | `dynamicClientRegistration.registrationAudience` | Required OB DCR Base62 ASPSP identifier |
| `issuer` | `dynamicClientRegistration.registrationIssuerOverride` | Prefer SSA derivation |
| `redirect_uris` | `dynamicClientRegistration.redirectUrisOverride` | Prefer derivation from the SSA `software_redirect_uris` claim |
| Signing certificate input | `dynamicClientRegistration.signingCertificatePath` | Reference only when claim construction needs it |
| `transport_cert_subject_dn` | `dynamicClientRegistration.transportCertificateSubjectDnOverride` | Prefer certificate derivation |
| `use_oid` | `dynamicClientRegistration.useNumericOidSubjectDn` | Retain numeric OID interoperability |
| `disablekeepalives` CLI flag | `dynamicClientRegistration.disableKeepAlive` | Retain only if runtime compatibility requires it |

Missing discovery, SSA, key, certificate, or derived claim data must fail
validation. The implementation must not fabricate fallback values.

## Approved corrections to legacy behavior

Each decision is classified in the JSON ledger as `corrected`, `strengthened`,
or `deliberately-unsupported`.

1. Respect every GET, PUT, and DELETE selection used by a scenario.
2. Report disabled coverage as `SKIPPED`, never passed.
3. Skip dependents after failed prerequisites instead of using invalid state.
4. Mask SSAs, JOSE, keys, client secrets, assertions, authorization headers,
   registration tokens, grant tokens, and token responses on every persisted
   or exported evidence surface.
5. Keep the fourth `DCR-011` trace step, but validate the expected error rather
   than decode it as a successful registration response.
6. Require an absolute HTTPS registration endpoint.
7. Apply complete DCR 3.4 schema and cross-field validation without localhost
   or other host-based shortcuts. This includes `native` application type, the
   512-character subject-DN constraint and pattern, the JWT bearer grant type,
   URI/algorithm/auth-method rules, and request/response consistency.
8. Accept only token auth methods the runtime can execute;
   `client_secret_post` remains deliberately unsupported.
9. Reject the legacy Ozone false positive: live verification must parse the
   structured result and fail when any conformance case fails. Matching a
   golden transcript is not evidence of success.

## Skip, pass/fail, and certification semantics

Results use only `passed`, `failed`, `warn`, and `skipped`. The top-level
`catalogue.traceGroups` hierarchy records each scenario, case, and step with its
final status, expected HTTP status, observed HTTP status when available, pinned
legacy provenance, and normative reference IDs.

- Cases excluded by an unselected optional endpoint are `skipped` with
  `skipReason: endpoint-not-selected`; a scenario with no selected cases is also
  explicitly skipped.
- A failed prerequisite produces `skipped` downstream runtime steps with
  `skipReason: failed-prerequisite`; it does not become a pass.
- Any failed or prerequisite-skipped executed mandatory step fails the run and
  blocks certification.
- A passing complete-coverage DCR result is certification-eligible only when all
  mandatory selected steps pass (or warn) and the tool version is in the supplied
  approved-release policy. Development mode, assertion overrides, missing policy,
  or an unapproved version remain explicit blockers.

Use the machine-readable operational gate:

```bash
uv run python -m conformance.result_gate out/test-results.json
```

It requires `status: passed`, `summary.failed: 0`, zero failed result steps, and
zero failed trace scenarios/cases/steps. The opt-in Ozone workflow dispatch
`run_dcr_34` builds a canonical plan from repository-managed credentials and
executes this gate. Local development has no live Ozone credentials, so offline
deterministic service tests are the default verification and are not evidence of
a live Ozone run.

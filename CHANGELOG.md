## [Unreleased]

### Added

- **Phase 2/3 endpoint-first catalogue migration**: Added schema v2 catalogue
  metadata for Read/Write catalogues, consolidated versioned catalogue files
  for `v3.1.11`, `v4.0.0` (with temporary `v4.0` alias), and `v4.0.1`, and
  parser/plugin tests covering resource groups, executable test metadata,
  field schemas, readiness policy, masking metadata, source coverage, and
  catalogue hash drift over policy metadata.
- **Phase 4 catalogue-native planner/executor foundation**: Added RunPlanV2
  compilation into catalogue dependency graphs, canonical predicate evaluation,
  shared Read/Write prerequisite de-duplication, resource-group-isolated
  token/PSU prerequisites, omitted mandatory coverage reporting, and a generic
  primitive-handler executor that skips only selected tests blocked by failed
  prerequisites.
- **Phase 5 DCR completion**: Migrated DCR 3.2, 3.3, and 3.4 catalogues to
  schema v2 metadata with selectable operations, primary `DCR-001`/`DCR-002`/
  `DCR-003`/`DCR-004`/`DCR-005`/`DCR-007`/`DCR-008`/`DCR-009`/`DCR-010`/
  `DCR-011` executable test IDs, non-certifying readiness policy, credential
  path masking metadata, catalogue-native GET/PUT/DELETE selection IDs, and
  masked DCR scenario NDJSON events for CLI/API runs.
- **Phase 6 field-value model and UI**: Made the staged browser plan builder
  catalogue-backed for Read/Write and DCR, including DCR specification/version
  selection, endpoint/operation coverage, catalogue-driven field and credential
  path prompts, live catalogue hash display, applicable test previews, readiness
  policy implications, omitted mandatory coverage, and saved config preview.
  The participant advanced panel now exposes raw `testTarget`/`testPlan` config
  preview/launch without manifest JSON authoring controls.
- **Phase 7 CLI/API convergence**: Added shared `testTarget` to RunPlanV2
  derivation using live plugin catalogue identity and hashes, and routed config
  `testTarget`/`testPlan` inputs through catalogue-native compilation before
  dispatch. DCR API launches now expose catalogue-derived scenario progress rows,
  and stale DCR operation IDs are rejected by catalogue validation before execution.
- **Phase 8 reporting and readiness**: Added catalogue-policy-backed
  `readinessReport` output for target-driven CLI/API Read/Write and DCR runs,
  including target coordinates, catalogue hash, selected coverage, omitted
  mandatory coverage, per-resource-group readiness/certification status, DCR
  non-certifying status, and masked evidence continuity through existing result
  and NDJSON log paths.
- **QA follow-up builder launch journey**: Added the enhanced one-file config
  document flow for the browser builder, including load/edit/export support,
  endpoint bulk selection controls, server-side OpenID discovery preview and
  empty-field prefill, staged launch routing through the shared target/test-plan
  planning path, and focused UI/API/CLI/config coverage for the contract.
- **Security hardening**: DCR now rejects `tlsSkipVerify: true` instead of
  constructing an HTTP client with TLS certificate verification disabled. Use
  `caBundlePath` to trust participant or ASPSP CA roots.

- **Stage 3 — CLI/API integration, `testSuite` removal, and hardening tests**:
  - `conformance/plan_executor.py`: New bridge module connecting `RunPlanV2` + `ModelBankConfig` to plugin-specific execution. Provides `build_default_registry()` (singleton `PluginRegistry` with `ReadWritePlugin` and `DcrPlugin`), `check_catalogue_drift()` (compares live catalogue hash against plan's stored hash), `execute_dcr_run()` (derives advertise flags from `endpoint_selections` and delegates to `DcrRunner`), `dcr_run_result_to_json_object()` (serialises `DcrRunResult` to JSON-ready dict with masked evidence), `resolve_rw_suite_for_plan()` (maps `specificationVersion` + resource group to a suite-catalog selection), and `utc_now()`.
  - `conformance/model_bank_config.py`: New `DcrConfig` frozen dataclass capturing file-backed DCR credentials and transport options. New `test_target: TestTargetConfig | None` and `dcr: DcrConfig | None` fields on `ModelBankConfig`. New `_parse_test_target_from_config()` and `_parse_dcr_config()` parsers. `tlsSkipVerify: true` is rejected because disabling TLS certificate verification is not allowed.
  - `conformance/cli.py`: Routes one-file config JSON documents with `testTarget`/`testPlan` through DCR (via `execute_dcr_run`) and Read/Write (via `resolve_rw_suite_for_plan`) without browser interaction, unless the selected tests require PSU/manual auth.
  - `conformance/api/views.py`: `POST /api/runs/` accepts config JSON with `testTarget`/`testPlan` and routes DCR or Read/Write plans through the plugin planning path.
  - `conformance/api/run_lifecycle.py`: `start_dcr_run()` and `_execute_dcr_run()` for async background DCR execution from the API.
  - `config/model-bank-dcr-example.json`: New example config for DCR 3.3 runs with `testTarget` and `dcr` sections.
  - `config/model-bank-rw-ais-example.json`: New example config for Read/Write AIS v4.0.1 runs with `testTarget`.
  - `tests/test_plan_executor.py`: Comprehensive tests for the `plan_executor` module covering registry building, catalogue drift detection, DCR run routing, and Read/Write suite resolution.

### Changed

- **Participant config contract tightened**: Generated/test-plan configs no longer
  require or export `environment`, `tls.certificatePathRoot`,
  `fapiSigning.certificatePathRoot`, or `dcr.credentialPathRoot`. TLS, FAPI
  signing, and DCR credential fields now use exact absolute file paths.
- **Saved test-plan drift enforcement**: CLI, REST API, and browser staged
  launch now reject saved `testPlan` documents when the stored catalogue hash
  differs from the bundled catalogue hash, requiring a fresh builder export.
- **Default Open Banking CA trust**: Read/Write and DCR HTTP clients now verify
  server certificates with system roots plus bundled public Open Banking
  production and pre-production CA roots inherited from the previous FCS.
  Participant-supplied `tls.caBundlePath`/`dcr.caBundlePath` values remain
  optional additive trust bundles for custom sandbox or ASPSP chains.
- **Browser saved-config contract tightened**: The staged browser journey now
  exports a single config JSON with top-level `testPlan`, removes the separate
  derived plan preview/copy surface, rejects retired `runPlan` imports with
  rebuild guidance, and filters Field Values to saved runtime config fields.
- **FAPI issuer/subject defaults and override model tightened**: Read/Write
  config parsing now rejects legacy `fapiSigning.clientAssertionIssuer` and
  `fapiSigning.clientAssertionSubject`, derives request-object and private-key
  JWT issuer/subject defaults from `oauth.clientId`, and introduces optional
  advanced override keys (`requestObjectIssuerOverride`,
  `privateKeyJwtIssuerOverride`, `privateKeyJwtSubjectOverride`) with
  `tls_client_auth` applicability validation. The staged planner now surfaces
  the new fields with conditional visibility and helper text, and bundled
  examples/documentation were updated to use the defaulted contract.

- **`testSuite` config key removed** (breaking): Participant configs that include `testSuite` will now fail with `ConfigError: Unknown config field(s): testSuite`. Migrate to `testTarget` using the updated example configs in `config/`. The `SuiteSelection` type is now internal-only (in `conformance/suite_catalog.py`) and is no longer part of the public config API.

- **`conformance/suite_catalog.py`**: `SuiteSelection`, `SuiteStandard`, `SuiteSpecVersion`, `SuiteApiFamily`, `SuiteProfile`, and `SuiteName` type aliases moved here from `conformance/model_bank_config.py`. These are now internal types used by `plan_executor.py` to map `RunPlanV2` coordinates to bundled manifests; they are not part of the participant-facing config API.

- **Config example files updated**: All seven `config/model-bank-*-example.json` files migrated from `testSuite` to `testTarget` shape.

- **README updated**: "Config-selected suite runs" section replaced with "Target-based conformance runs" documenting the one-file `testTarget`/`testPlan` config shape for both Read/Write and DCR runs.


  - `conformance/plugins/read_write/`: `ReadWritePlugin` implementing `ConformancePlugin` for OB Read/Write v4.0.1. Covers AIS (28 endpoints), PIS (14), CBPII (4), and VRP (7) resource groups across versioned JSON catalogues under `conformance/plugins/read_write/catalogues/v4_0_1/`. Each entry records endpoint ID, HTTP method, path, resource group, mandatory/conditional/optional requirement level, display label, schema ref (to bundled v4.0.1 OpenAPI snapshots), and test applicability rules. Content-hash-based drift detection via `CatalogueIdentity`.
  - `conformance/plugins/dcr/`: Native Python DCR plugin with full support for DCR 3.2, 3.3, and 3.4. Preserves all legacy scenario IDs (DCR-001 through DCR-011). Implements OIDC discovery fetch and FAPI auth method selection (`tls_client_auth` preferred over `private_key_jwt`), PS256/RS256 registration JWT generation, POST/GET/PUT/DELETE registration lifecycle, client-credentials token grants, negative test cases (expired SSA, invalid issuer, invalid auth method, wrong response type, deleted/wrong client ID), per-version schema validation, and best-effort cleanup via DELETE. All sensitive values (`client_secret`, `registration_access_token`, `access_token`) are masked via `conformance.masking` before inclusion in any evidence. Reuses Stage 1 `DcrCredentialPaths` and `DcrTransportConfig` primitives.
  - `conformance/results.py` (readiness model): New `RunReadinessReport` type with `SelectedCoverageSummary`, per-resource-group `ResourceGroupReadiness`, and `DcrReadinessStatus`. Outcome logic produces `ready` / `incomplete` / `non-certifying` / `failed`. DCR runs are always `non-certifying` until a formal certification policy exists. `skipped` is reserved exclusively for selected tests blocked by runtime prerequisites; unselected coverage does not appear in the report. Omitting mandatory endpoints marks the affected resource group as `incomplete` but does not block execution.
  - Plan-builder UI rebuilt (`conformance/api/templates/conformance/plan_builder.html`): Staged 8-step journey (Standard -> Specification -> Security Profile badge -> Version -> Resource Group(s)/Operations -> Endpoint Coverage -> Field Values -> Preview). Required endpoints are preselected but removable. JSON/config import moved into a collapsed "Advanced / Import JSON" `<details>` section. Legacy suite-centric controls removed.

- **Stage 1 foundation trunk — plugin framework, target model, catalogue loader, DCR primitives, and Run Plan v2**:
  - `conformance/plugins/domain.py`: `ConformancePlugin` structural Protocol, `PluginTargetMetadata`, and `PluginId` type alias. Defines the full plugin interface contract (target metadata, catalogue identity, catalogue loader, target applicability predicate, masking fields) that every internal plugin must satisfy.
  - `conformance/plugins/registry.py`: `PluginRegistry` — ordered registration and target-based resolution of `ConformancePlugin` instances. Raises `PluginRegistryError` on duplicate registration or unresolvable target.
  - `conformance/target_config.py`: `TestTargetConfig` frozen dataclass replacing the legacy `testSuite` config shape. Introduces `Standard`, `Specification`, and `SecurityProfile` literals, plus `parse_test_target_config` / `serialise_test_target_config` with camelCase JSON wire format.
  - `conformance/catalogue.py`: Versioned JSON catalogue domain types (`CatalogueIdentity`, `EndpointCatalogueEntry`, `Catalogue`, `EndpointRequirement`) and `parse_catalogue` / `compute_catalogue_hash` functions. Content hashing uses the same `"sha256:<hex>"` format as the Run Plan v1 manifest hash.
  - `conformance/dcr/credentials.py`: `DcrCredentialPaths`, `DcrCredentials`, `validate_dcr_credential_paths`, and `load_dcr_credentials`. File-backed DCR credential loading (SSA, signing key/cert, transport cert/key, CA bundle) with exact absolute path validation and no credential-content persistence.
  - `conformance/dcr/transport.py`: `DcrTransportConfig` frozen dataclass capturing mTLS transport options (`token_endpoint_auth_method`, `disable_keep_alives`, `tls_skip_verify`, timeouts). `tls_skip_verify=True` emits an explicit unsafe warning. `DcrTokenEndpointAuthMethod` restricts token-endpoint auth to FAPI 1 Advanced-compatible `tls_client_auth` and `private_key_jwt`.
  - `conformance/run_plan_v2.py`: Schema version `"2"` intent-based `RunPlanV2` replacing suite-centric `RunPlanSuiteCoordinates` with `RunPlanV2TargetCoordinates` (standard, specification, securityProfile, specificationVersion, catalogueHash). Stores user intent — resource groups, per-endpoint `EndpointSelection` with field values, and test data — from which the engine derives applicable tests at execution time. Includes `parse_run_plan_v2`, `serialise_run_plan_v2`, and `RunPlanV2ParseError`.

### Changed

- **v4.0.1 AIS resource path correction**: The v4.0.1 AIS certification baseline and slice suite manifests now use `/open-banking/v4.0/aisp/...` resource URLs instead of `/open-banking/v4.0.1/aisp/...`. This aligns with the bundled v4.0.1 OpenAPI `servers` URL and model-bank deployment behaviour; the v4.0 path family is shared across the v4.0 minor release. Suite granularity (schema document id `ob-read-write-v4.0.1-account-info-openapi`, manifest filename, catalog labels) remains v4.0.1-specific.

- **Model bank AIS baseline example configs updated to v4.0.1**: `config/model-bank-ais-certification-baseline-example.json` now selects `specVersion: v4.0.1`. A new explicit `config/model-bank-ais-certification-baseline-v4.0.1-example.json` is also provided for participants who want a version-named config file.

- **Plan Builder test-data snapshot**: `testData.values` in exported saved config JSON is now a full executable snapshot rather than a delta-only document. The snapshot includes manifest baseline values for all allow-listed keys referenced by selected steps, overlaid with any participant-supplied values from config or the Plan Builder form. Certification value purity is determined by comparing the snapshot against the manifest baseline via `RunConfiguration.baseline_delta_keys`; a saved config that stores baseline-equal values is not marked as exploratory. The `_is_exploratory_run` helper now uses `baseline_delta_keys` for new-schema manifests instead of checking whether `testData.values` is non-empty.



- **Breaking Custom Test Values redesign**: suite manifests now own `testValues.baseline`, `generatedKeys`, and `allowedCustomKeys`; participant configs and run plans now use `testData.values`; the compiled `RunConfiguration` is the execution artifact; certification now uses separate coverage and value-purity gates; launch is blocked when required keys are missing from both baseline and participant data; and result evidence now records baseline-delta impact (`testValueProfile.baselineDeltaKeys`, `customTestValueImpact.baselineDeltaKeyCount`) with UI labels that only appear when genuine deltas exist.

### Fixed

- `funds-confirmation` step in the PIS domestic-payment starter suite now correctly uses the PSU-authorised `token-exchange` access token instead of the client-credentials token. Ozone and compliant ASPSPs require a PSU-scoped payment token to access the `/domestic-payment-consents/{id}/funds-confirmation` endpoint; the prior client-credentials token produced a `401` on every run.

- PIS domestic-payment starter consent and submission bodies now pass Ozone/OB schema validation. `InstructionIdentification` and `EndToEndIdentification` are generated using a new `per-run-compact-uuid` profile kind (UUID4 hex, 32 characters) which satisfies the OB PIS 35-character field limit. `RemittanceInformation.Unstructured` is now rendered as a JSON array as required by the Open Banking Read/Write v4.0 API specification.

- Plan Builder Custom Test Value reset controls are now hidden while a field matches its selected profile default, appear live when the participant edits a value, and restore the default in-place without submitting the page or collapsing the current tree view.

- The PIS domestic-payment starter `psu-authorization-signing-negative` step now runs in headless mode with an explicit expected authorisation-endpoint rejection (`HTTP 400`). Ozone's direct invalid-request error page no longer causes a manual PSU timeout when this intentionally invalid request-object check runs, and Ozone-style non-callback redirect rejections now also satisfy that explicit negative expectation without weakening normal redirect safety checks.

- The `pis-fcs-legacy-benchmark` manifest now uses per-flow compact UUID identifiers instead of reusing one instruction/end-to-end pair across independent consent journeys, adds `Data.Permission: "Create"` to scheduled-consent request bodies, and requires `finalPaymentDateTime` for standing-order row selection. This removes duplicate identifier and missing field errors seen against Ozone/model-bank benchmark runs while preserving optional-row gating behavior.

- The executable domestic-payment, domestic-scheduled-payment, and domestic-standing-order chains in `pis-fcs-legacy-benchmark` now authorise and submit no-debtor consent payloads (`OB-400-DOP-100100`, `OB-400-DOP-100800`, and `OB-400-DOP-101200`) while retaining debtor-account variants (`OB-400-DOP-100300`, `OB-400-DOP-100820`) as standalone consent-creation coverage rows. This avoids the Ozone model-bank PSU app rejecting debtor-account consent authorisation with `404 Debtor Account` while preserving legacy row coverage.

- The v4.0 PIS `pis-fcs-legacy-benchmark` scheduled and standing-order rows now align to legacy/Ozone execution semantics: `OB-400-DOP-101101` uses a consent-bound PSU/token chain for `OB-400-DOP-101000`, standing-order consent/submission payloads now use `Data.Permission` plus `Initiation.MandateRelatedInformation` shape, `OB-400-DOP-101400` is a signed invalid-frequency negative (not missing-JWS), and `OB-400-DOP-101503` is a signed both-fields (`FinalPaymentDateTime` + `Frequency.CountPerPeriod`) consent negative so the known model-bank `201` vs expected `400` behaviour is surfaced correctly.

- The v4.0 PIS `pis-fcs-legacy-benchmark` now closes documented legacy parity gaps by bundling and allowlisting the v4.0 payment-initiation OpenAPI snapshot, adding `response_schema` assertions across legacy `schemaCheck` rows, restoring signature-negative semantics (`OB-400-DOP-100110` now uses `omit-jwt-claim` plus one-of OB signature error codes; `OB-316-DOP-100310` now asserts `UK.OBIE.Signature.Missing`), adding `response_signature` assertions for legacy `validateSignature: true` rows, and marking conditional rows as `selectionMetadata.conditional: true` so legacy rows are default-selected when required test values are present.

### Security

- PSU authorisation URLs now mask credential-bearing query parameters before being embedded in step results, `details.request.url`, placeholder-addressable execution context request URLs (`${steps.<id>.request.url}`), buffered execution-log events, or API log snapshots. The masking covers OAuth/JAR `request`, `request_object`, and `client_assertion` values (plus the existing credential-key set), while keeping non-sensitive URL context such as the endpoint, `client_id`, `redirect_uri`, `response_type`, `scope`, and `state` visible for debugging.
- Interactive CLI manifest runs still print the raw browser-facing `psu-authorization-url` to stderr so participants can complete manual consent. The raw URL is read by the CLI logger decorator from the in-memory event before `BufferedExecutionLogger` stores the masked payload; copied `client_id` and `request_object` fields are also masked in persisted logs.
- Browser-launched manual PSU authorisation runs expose the raw authorisation URL only through process-local, in-memory run state while the active run is awaiting participant action. The pending action clears after callback receipt, matching step completion, run completion, application failure, or terminal-record pruning, and the raw URL is not persisted to result JSON, NDJSON execution logs, API log snapshots, or downloadable artifacts.
- PSU authorization callback endpoint at the project root (`GET /callback/`) is **intentionally not loopback-guarded**, unlike every other API endpoint in this codebase. An ASPSP browser redirect must be able to reach it, and even when the FCS runs locally the navigation arrives via the host's network stack; coupling the endpoint to `REMOTE_ADDR` would break reverse-proxy deployments without adding real security. The security model relies on three independent properties instead: `state` token unguessability (prefer server-generated values via `secrets.token_urlsafe(32)` — 32 bytes of entropy; caller-supplied values are only length-validated and rejected with HTTP 400 below 32 characters, so callers MUST ensure they are cryptographically unguessable), one-shot consumption (a second hit on the same `state` is rejected and does not overwrite the captured value), and run-scoped binding (the loopback-guarded read API `GET /api/runs/<id>/auth-sessions/<state>/` requires the parent run id to retrieve the captured `code`). The callback never echoes the `state` value or any ASPSP-supplied free text into the response body, and every failure mode (unknown state, missing state, already-resolved session) returns an identical generic 400 page so an unauthenticated caller cannot enumerate which states the store knows about. Unknown-state hits deliberately do **not** emit an execution-log event — there is no run context to attach to, and emitting one would partially defeat the non-enumerability property. CSRF exemption is not required: the endpoint is `GET`-only (enforced by `require_GET`); if a future change adds `POST`, the CSRF posture must be revisited.
- Authorization `code` values captured from the ASPSP redirect are added to the `conformance.masking` sensitive-key set so the raw `code` is replaced with the literal `"***"` before being buffered by `BufferedExecutionLogger` (unless masking is disabled via `CONFORMANCE_DEVELOPER_MODE=true` for local debugging). The clear-text `code` is only exposed via the loopback-guarded `GET /api/runs/<id>/auth-sessions/<state>/` endpoint (intended for one-shot consumption by the run driver), and is not persisted to the NDJSON execution log on disk by default. Per-run cap of 8 simultaneous auth sessions bounds in-memory growth and limits the blast radius of a buggy driver that registers without ever consuming.

- Docker base image switched from `python:3.14.4-slim-bookworm` (Debian) to `python:3.14.5-alpine3.22` (Alpine) in both builder and runtime stages. The distro switch eliminates the bulk of upstream Debian OS-package CVEs flagged by Snyk on the bookworm-slim image, and selecting the `.5` Alpine patch (rather than `.4`) additionally clears a medium-severity CVE Snyk flagged against the 3.14.4 patch image. The stable Python 3.14 line is retained (matches `requires-python = ">=3.14.4"` in `pyproject.toml`); Snyk's suggested `python:3.15-rc-alpine3.22` was deliberately not adopted because a release-candidate interpreter is inappropriate for a regulated financial-services conformance tool. The builder stage now installs `build-base`, `libffi-dev`, `cargo`, and `rust` so any C/Rust extensions pulled in by `uvicorn[standard]` (`httptools`, `uvloop`, `watchfiles`) that lack musl wheels can compile from source — all build tooling stays in the discarded builder layer. Non-root user creation switched from Debian's `groupadd`/`useradd` to Alpine's BusyBox `addgroup`/`adduser` (UID/GID 1000 unchanged). Runtime behaviour, exposed port, `HEALTHCHECK`, and `CMD` are unchanged.
- Manifest URLs now reject IP-literal hostnames to harden against SSRF in manifest-driven HTTP execution.

Runtime scheduling now executes selected setup steps sequentially before execution-phase steps, runs independent execution groups concurrently within a single active run while preserving sequential order inside each group, continues other groups when one group fails, and merges outcomes in deterministic manifest order for reporting. This slice creates the catalog rail only; it does not add full OB Read/Write v3.1.11 or v4.0 certification coverage.

While a manual PSU step awaits callback, the run detail page and status partial show an `Open authorisation` action for the current step.

The validator accepts `passed` and `warn` mandatory steps, rejects failed/skipped/missing mandatory coverage and unapproved tool versions, emits a Confluence-ready summary, and includes an example non-authoritative approved-release policy file.
- Generated result JSON now includes stable report metadata and the FCS tool version so OBL-side validation can confirm submitted reports were produced by an approved release. Release builds can stamp the version with `CONFORMANCE_TOOL_VERSION`; source runs fall back to `[project].version` and then `0+unknown`.
- New v1 manifest step kind `psu-authorization` (manual + headless modes) drives the existing `AuthSessionStore` and `/callback/` plumbing end-to-end, completing FAPI hybrid-flow authorisation as a first-class manifest step. Implements PRD Participant Stories #8 (manual PSU guidance), #9 (headless for CI), and #17 (FAPI 1 Advanced hybrid flow). Tracking issue #29.

- v1 manifest steps gain an optional `kind` discriminator (`"http"` — default, or `"psu-authorization"`) and a new `psu-authorization` step shape parsed into a sibling `PsuAuthorizationStep` dataclass alongside `ManifestStep`. PSU steps carry `mode` (`"manual"` or `"headless"`), `authorizationEndpoint` (placeholders allowed; HTTPS-validated at parse time when no placeholder is present), `clientId` (placeholders allowed), `redirectUri` (HTTPS-validated at parse time; placeholders **rejected** — defence in depth against open-redirect bypass in headless mode), optional `responseType` (defaults to `"code id_token"` for FAPI 1 Advanced hybrid flow), optional `scope` (defaults to `"openid"`), optional `state` (placeholders allowed; literal values are rejected below 32 characters to mirror `AuthSessionStore`'s `MIN_CALLER_SUPPLIED_STATE_LENGTH`), optional `requestObject` (placeholders allowed; treated as an opaque JWT), optional `timeoutSeconds` (default 120, range 1–600 inclusive — booleans rejected so a misauthored `true`/`false` cannot silently become a 1- or 0-second timeout), and the existing `mandatory`/`optional` flags with the same mutual-exclusion rule. PSU-only fields are rejected on HTTP steps and HTTP-only fields (`request`, `assertions`, `warning`) are rejected on PSU steps so a typo in one shape cannot silently fall through to the other. `Manifest.steps` is now a tuple of `ManifestStep | PsuAuthorizationStep`. A new bundled example manifest at `config/manifest-v1-psu-authorization-example.json` demonstrates the discovery → PSU authorisation → token-exchange flow. Implements Phase 2 of the PSU authorisation manifest-step plan; executor dispatch for PSU steps lands in Phase 3.
- Manual `psu-authorization` manifest steps now execute end-to-end. The executor resolves authorisation endpoint/client/state/request-object placeholders, registers an in-process `AuthSessionStore` session for the run, builds the FAPI hybrid-flow authorisation URL with standard-library query encoding, emits a `psu-authorization-url` execution-log event for the participant/browser hand-off, polls until `/callback/` captures either a `code` or ASPSP error, and records a synthetic response so downstream steps can use `${steps.<id>.response.body.code}` for token exchange. Timeouts and auth-session registration errors fail the step with masked request evidence.
- Headless `psu-authorization` manifest steps now issue the authorisation GET with redirect following disabled, require a 3xx `Location` response, verify the redirect target matches the configured `redirectUri`, parse `state` plus `code` or OAuth error from the redirect URL, and feed the outcome through the same `AuthSessionStore` and synthetic-response path as manual mode. The live Ozone feasibility question remains the PRD open investigation item; the live tier-2 test is gated on `OZONE_HEADLESS_PSU_SUPPORTED=true` and skips unless the capability is explicitly enabled.
- CLI manifest runs now mirror `psu-authorization-url` events to interactive stderr as a single `[PSU] Open this URL to authorise: <url>` line whenever stdout is attached to a TTY, so manual PSU consent runs give the participant the browser hand-off URL without requiring them to tail NDJSON. Buffered execution logs and `GET /api/runs/<id>/log/` expose the same event with sensitive URL query parameters masked. The REST API path is covered end-to-end by a test that starts a PSU manifest run, completes it through `/callback/`, and verifies a PASS result.

- PSU authorization callback coordination plumbing (PRD PSU Authorisation, Phase 1 manual mode). Three new HTTP surfaces are added so the engine can correlate an inbound ASPSP browser redirect back to a known run: `POST /api/runs/<run_id>/auth-sessions/` (loopback-guarded; registers an expected `state` token and returns it for the run driver to embed in the authorization URL — empty body asks the server to generate a 32-byte `secrets.token_urlsafe` token; an optional `{"state": "..."}` body lets the caller supply their own, subject to a 32-character minimum length); `GET /api/runs/<run_id>/auth-sessions/<state>/` (loopback-guarded; returns `{state, status, createdAt, capturedAt?, code?, error?, errorDescription?}` so the driver can poll for completion and consume the captured `code` exactly once); and `GET /callback/` mounted at the project root (public — see Security entry — receives `?state=&code=` on success or `?state=&error=&error_description=` on failure, records the outcome on the session, and renders a minimal HTML landing page from `conformance/api/templates/conformance/callback.html`). A new in-memory `AuthSessionStore` (sibling to `RunStore`, threading-locked, process-local, ephemeral) holds the sessions with terminal states `captured` and `error`, one-shot transition semantics, a per-run cap of 8 sessions, and a `discard_for_run` hook called when the parent run reaches a terminal state so awaiting sessions don't outlive their parent. Two new execution-log event types — `auth-session-registered` (payload `{state, status: "awaiting"}`) and `auth-callback-received` (payload `{state, code: "***"}` on success or `{state, error, error_description}` on the ASPSP-reported-error variant, snake_case to match the rest of the event taxonomy) — join the closed taxonomy and are emitted into the parent run's execution log so a log consumer can reconstruct the full flow without scanning the run driver's own traces. Token exchange of the captured `code` (using `conformance.http`'s mTLS primitives) and an executor-side `awaitAuthorizationCode` step type are explicit follow-up PRs and are out of scope here.

- First-class `TestPlan` model with mandatory pre-population and explicit deselection (PRD Participant Story #4; OBL Standards Story #3). v1 manifest steps may now declare an optional `"optional": true|false` flag (default `false`) parsed strictly as a JSON boolean; `mandatory` and `optional` are mutually exclusive at parse time. The new `conformance.test_plan` module exposes `TestPlan` and `TestPlanEntry` dataclasses with `default_plan_from_manifest()` (selects every mandatory + non-optional step), `with_deselection()` (returns a new immutable plan with named step ids deselected — unknown ids raise `ValueError`), `selected_step_ids()`, `deselected_mandatory_step_ids()`, `is_eligible_by_selection()`, and `summary()`. The executor accepts a `plan` keyword on `run_manifest()`: deselected steps do **not** run and produce **no** `StepResult` (they are not the same as `SKIPPED`). When `plan` is omitted the engine builds the default plan from the manifest, preserving the previous behaviour exactly. The CLI gains a repeatable `--deselect STEP_ID` flag (manifest mode only — exits 2 if combined with no `--manifest` or if an id is unknown). The REST API accepts an optional `"deselectStepIds": [str, ...]` field on `POST /api/runs/`, validated against the inline manifest at request time (HTTP 400 on unknown ids or when supplied without an inline manifest). A new `step-deselected` event type joins the execution-log taxonomy and is emitted once per deselected step before any `step-started`, so a log consumer can read the plan-vs-manifest delta without scanning the entire run.
- Gated tier-2 Ozone headless PSU integration coverage runs only when both `OZONE_DISCOVERY_URL` and `OZONE_HEADLESS_PSU_SUPPORTED=true` are set; the workflow dispatch surface includes the opt-in flag and otherwise skips with the PRD open-investigation reason.
- Structured execution log written alongside every result file, exposed through `GET /api/runs/<id>/log/`, and masked by default with `CONFORMANCE_DEVELOPER_MODE=true` reserved for local debugging.
- Defence-in-depth loopback guard, bounded terminal-run history, REST API run surfaces, and `load_manifest_from_object()` support for local headless/CI usage.

The previous "skip parsing for multipart" branch (added to accommodate Django's test client posting an empty multipart envelope for `client.post(url)` with no data) would have silently dropped a caller-supplied `state` posted as multipart form fields, reintroducing the silent-drop class of bug the parse-at-the-boundary change was meant to prevent. Empty multipart envelopes (no fields, no files) are still accepted as bodyless. Addresses Copilot PR #28 review feedback.

Previously the active-run check ran before `register(...)` and `_execute_run`'s `discard_for_run` cleanup could fire between the two calls, leaving an orphaned `awaiting` session that outlived its parent run. The endpoint now returns 404 (run pruned) or 409 (run terminal) instead of 201 in that race; the happy-path response is unchanged.

- `RunStore.get_run_log_bytes()` now snapshots the `execution_logger` reference under the store lock and serialises the NDJSON buffer outside the lock. Previously the full `to_ndjson_bytes()` call (JSON-serialising every buffered event) ran while holding the store lock, unnecessarily blocking concurrent `status/result` updates and `create_run` calls for the duration of serialisation. `BufferedExecutionLogger` already protects its own buffer with a per-instance lock so snapshot-then-serialise is thread-safe.

Previously, a developer with `DJANGO_SECRET_KEY=django-insecure-...` exported in their shell (the documented dev value) would see `mypy` crash with `Error constructing plugin instance of NewSemanalDjangoPlugin` because the Django plugin imports `config.settings` during construction and the guard refused to load. The guard still fires for `python`/`uvicorn`/`gunicorn` server invocations — the deployment safeguard is unchanged.
- `run_model_bank_smoke_check` now emits an `application-error` event (with `{"message": str(error)}`) before re-raising any unexpected exception that escapes the engine body after `run-started` has been emitted. Previously, an exception raised from `OzoneModelBankClient.from_config` (or any future unexpected engine bug) would leave the execution log ending with only `run-started`, breaking the log contract introduced in PR #22. The original exception still propagates unchanged so CLI and API error-handling is unaffected.
- `GET /api/runs/<id>/log/` now returns HTTP 500 (`{"error": "Execution log unavailable for this run"}`) when the run record exists but has no attached execution logger, rather than the incorrect HTTP 404 that was returned for both "unknown run" and "logger not attached". The 404 path (`"Run not found"`) is unchanged. The logger-absent path is an invariant violation in production code; 500 is appropriate.

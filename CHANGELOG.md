### Security

- PSU authorisation URLs now mask credential-bearing query parameters before being embedded in step results, `details.request.url`, placeholder-addressable execution context request URLs (`${steps.<id>.request.url}`), buffered execution-log events, or API log snapshots. The masking covers OAuth/JAR `request`, `request_object`, and `client_assertion` values (plus the existing credential-key set), while keeping non-sensitive URL context such as the endpoint, `client_id`, `redirect_uri`, `response_type`, `scope`, and `state` visible for debugging.
- Interactive CLI manifest runs still print the raw browser-facing `psu-authorization-url` to stderr so participants can complete manual consent. The raw URL is read by the CLI logger decorator from the in-memory event before `BufferedExecutionLogger` stores the masked payload; copied `client_id` and `request_object` fields are also masked in persisted logs.
- Browser-launched manual PSU authorisation runs expose the raw authorisation URL only through process-local, in-memory run state while the active run is awaiting participant action. The pending action clears after callback receipt, matching step completion, run completion, application failure, or terminal-record pruning, and the raw URL is not persisted to result JSON, NDJSON execution logs, API log snapshots, or downloadable artifacts.
- PSU authorization callback endpoint at the project root (`GET /callback/`) is **intentionally not loopback-guarded**, unlike every other API endpoint in this codebase. An ASPSP browser redirect must be able to reach it, and even when the FCS runs locally the navigation arrives via the host's network stack; coupling the endpoint to `REMOTE_ADDR` would break reverse-proxy deployments without adding real security. The security model relies on three independent properties instead: `state` token unguessability (prefer server-generated values via `secrets.token_urlsafe(32)` — 32 bytes of entropy; caller-supplied values are only length-validated and rejected with HTTP 400 below 32 characters, so callers MUST ensure they are cryptographically unguessable), one-shot consumption (a second hit on the same `state` is rejected and does not overwrite the captured value), and run-scoped binding (the loopback-guarded read API `GET /api/runs/<id>/auth-sessions/<state>/` requires the parent run id to retrieve the captured `code`). The callback never echoes the `state` value or any ASPSP-supplied free text into the response body, and every failure mode (unknown state, missing state, already-resolved session) returns an identical generic 400 page so an unauthenticated caller cannot enumerate which states the store knows about. Unknown-state hits deliberately do **not** emit an execution-log event — there is no run context to attach to, and emitting one would partially defeat the non-enumerability property. CSRF exemption is not required: the endpoint is `GET`-only (enforced by `require_GET`); if a future change adds `POST`, the CSRF posture must be revisited.
- Authorization `code` values captured from the ASPSP redirect are added to the `conformance.masking` sensitive-key set so the raw `code` is replaced with the literal `"***"` before being buffered by `BufferedExecutionLogger` (unless masking is disabled via `CONFORMANCE_DEVELOPER_MODE=true` for local debugging). The clear-text `code` is only exposed via the loopback-guarded `GET /api/runs/<id>/auth-sessions/<state>/` endpoint (intended for one-shot consumption by the run driver), and is not persisted to the NDJSON execution log on disk by default. Per-run cap of 8 simultaneous auth sessions bounds in-memory growth and limits the blast radius of a buggy driver that registers without ever consuming.

- Docker base image switched from `python:3.14.4-slim-bookworm` (Debian) to `python:3.14.5-alpine3.22` (Alpine) in both builder and runtime stages. The distro switch eliminates the bulk of upstream Debian OS-package CVEs flagged by Snyk on the bookworm-slim image, and selecting the `.5` Alpine patch (rather than `.4`) additionally clears a medium-severity CVE Snyk flagged against the 3.14.4 patch image. The stable Python 3.14 line is retained (matches `requires-python = ">=3.14.4"` in `pyproject.toml`); Snyk's suggested `python:3.15-rc-alpine3.22` was deliberately not adopted because a release-candidate interpreter is inappropriate for a regulated financial-services conformance tool. The builder stage now installs `build-base`, `libffi-dev`, `cargo`, and `rust` so any C/Rust extensions pulled in by `uvicorn[standard]` (`httptools`, `uvloop`, `watchfiles`) that lack musl wheels can compile from source — all build tooling stays in the discarded builder layer. Non-root user creation switched from Debian's `groupadd`/`useradd` to Alpine's BusyBox `addgroup`/`adduser` (UID/GID 1000 unchanged). Runtime behaviour, exposed port, `HEALTHCHECK`, and `CMD` are unchanged.
- Manifest URLs now reject IP-literal hostnames to harden against SSRF in manifest-driven HTTP execution.

### Added

- Group-aware v1 manifest execution semantics. Manifest steps now support additive scheduling metadata (`phase`: `setup|execution`, default `execution`; `group`, default `default`) across HTTP and `psu-authorization` step kinds, with parse-time validation and backward compatibility for existing v1 manifests. Runtime scheduling now executes selected setup steps sequentially before execution-phase steps, runs independent execution groups concurrently within a single active run while preserving sequential order inside each group, continues other groups when one group fails, and merges outcomes in deterministic manifest order for reporting. Participant-facing plan preview surfaces now display step phase/group metadata. This adds engine scheduling behaviour only and does not yet add full Open Banking Read/Write certification-suite coverage.
- Config-driven suite resolution from participant configuration. A new optional `testSuite` object selects bundled smoke-level Open Banking Read/Write discovery/JWKS manifests for `v3.1.11` or `v4.0` under the `fapi1-advanced` profile, with safe runtime manifest placeholders limited to `${config.discoveryUrl}` and `${config.environment}`. CLI, REST API, and browser plan-builder flows now use the config-selected suite when no explicit manifest is supplied, preserve explicit manifests as an override, and add suite metadata to suite-resolved result/log output. This slice creates the catalog rail only; it does not add full OB Read/Write v3.1.11 or v4.0 certification coverage.
- Participant-facing Django-template plan builder and run monitoring UI. Participants can open `/plan/`, paste model-bank config JSON plus a v1 manifest, preview mandatory/non-optional/default-optional step selection, see the certification impact of deselecting mandatory steps, launch browser-supported runs including manual PSU authorisation manifests, and monitor status, masked logs, and result summaries at `/runs/<run_id>/`. While a manual PSU step awaits callback, the run detail page and status partial show an `Open authorisation` action for the current step.
- OBL-side certification report validator CLI for checking submitted result JSON against the original manifest's mandatory criteria and an externally supplied approved-release policy. The validator accepts `passed` and `warn` mandatory steps, rejects failed/skipped/missing mandatory coverage and unapproved tool versions, emits a Confluence-ready summary, and includes an example non-authoritative approved-release policy file.
- Generated result JSON now includes stable report metadata and the FCS tool version so OBL-side validation can confirm submitted reports were produced by an approved release. Release builds can stamp the version with `CONFORMANCE_TOOL_VERSION`; source runs fall back to `[project].version` and then `0+unknown`.
- New v1 manifest step kind `psu-authorization` (manual + headless modes) drives the existing `AuthSessionStore` and `/callback/` plumbing end-to-end, completing FAPI hybrid-flow authorisation as a first-class manifest step. Implements PRD Participant Stories #8 (manual PSU guidance), #9 (headless for CI), and #17 (FAPI 1 Advanced hybrid flow). Tracking issue #29.

- v1 manifest steps gain an optional `kind` discriminator (`"http"` — default, or `"psu-authorization"`) and a new `psu-authorization` step shape parsed into a sibling `PsuAuthorizationStep` dataclass alongside `ManifestStep`. PSU steps carry `mode` (`"manual"` or `"headless"`), `authorizationEndpoint` (placeholders allowed; HTTPS-validated at parse time when no placeholder is present), `clientId` (placeholders allowed), `redirectUri` (HTTPS-validated at parse time; placeholders **rejected** — defence in depth against open-redirect bypass in headless mode), optional `responseType` (defaults to `"code id_token"` for FAPI 1 Advanced hybrid flow), optional `scope` (defaults to `"openid"`), optional `state` (placeholders allowed; literal values are rejected below 32 characters to mirror `AuthSessionStore`'s `MIN_CALLER_SUPPLIED_STATE_LENGTH`), optional `requestObject` (placeholders allowed; treated as an opaque JWT), optional `timeoutSeconds` (default 120, range 1–600 inclusive — booleans rejected so a misauthored `true`/`false` cannot silently become a 1- or 0-second timeout), and the existing `mandatory`/`optional` flags with the same mutual-exclusion rule. PSU-only fields are rejected on HTTP steps and HTTP-only fields (`request`, `assertions`, `warning`) are rejected on PSU steps so a typo in one shape cannot silently fall through to the other. `Manifest.steps` is now a tuple of `ManifestStep | PsuAuthorizationStep`. A new bundled example manifest at `config/manifest-v1-psu-authorization-example.json` demonstrates the discovery → PSU authorisation → token-exchange flow. Implements Phase 2 of the PSU authorisation manifest-step plan; executor dispatch for PSU steps lands in Phase 3.
- Manual `psu-authorization` manifest steps now execute end-to-end. The executor resolves authorisation endpoint/client/state/request-object placeholders, registers an in-process `AuthSessionStore` session for the run, builds the FAPI hybrid-flow authorisation URL with standard-library query encoding, emits a `psu-authorization-url` execution-log event for the participant/browser hand-off, polls until `/callback/` captures either a `code` or ASPSP error, and records a synthetic response so downstream steps can use `${steps.<id>.response.body.code}` for token exchange. Timeouts and auth-session registration errors fail the step with masked request evidence.
- Headless `psu-authorization` manifest steps now issue the authorisation GET with redirect following disabled, require a 3xx `Location` response, verify the redirect target matches the configured `redirectUri`, parse `state` plus `code` or OAuth error from the redirect URL, and feed the outcome through the same `AuthSessionStore` and synthetic-response path as manual mode. The live Ozone feasibility question remains the PRD open investigation item; the live tier-2 test is gated on `OZONE_HEADLESS_PSU_SUPPORTED=true` and skips unless the capability is explicitly enabled.
- CLI manifest runs now mirror `psu-authorization-url` events to interactive stderr as a single `[PSU] Open this URL to authorise: <url>` line whenever stdout is attached to a TTY, so manual PSU consent runs give the participant the browser hand-off URL without requiring them to tail NDJSON. Buffered execution logs and `GET /api/runs/<id>/log/` expose the same event with sensitive URL query parameters masked. The REST API path is covered end-to-end by a test that starts a PSU manifest run, completes it through `/callback/`, and verifies a PASS result.

- PSU authorization callback coordination plumbing (PRD PSU Authorisation, Phase 1 manual mode). Three new HTTP surfaces are added so the engine can correlate an inbound ASPSP browser redirect back to a known run: `POST /api/runs/<run_id>/auth-sessions/` (loopback-guarded; registers an expected `state` token and returns it for the run driver to embed in the authorization URL — empty body asks the server to generate a 32-byte `secrets.token_urlsafe` token; an optional `{"state": "..."}` body lets the caller supply their own, subject to a 32-character minimum length); `GET /api/runs/<run_id>/auth-sessions/<state>/` (loopback-guarded; returns `{state, status, createdAt, capturedAt?, code?, error?, errorDescription?}` so the driver can poll for completion and consume the captured `code` exactly once); and `GET /callback/` mounted at the project root (public — see Security entry — receives `?state=&code=` on success or `?state=&error=&error_description=` on failure, records the outcome on the session, and renders a minimal HTML landing page from `conformance/api/templates/conformance/callback.html`). A new in-memory `AuthSessionStore` (sibling to `RunStore`, threading-locked, process-local, ephemeral) holds the sessions with terminal states `captured` and `error`, one-shot transition semantics, a per-run cap of 8 sessions, and a `discard_for_run` hook called when the parent run reaches a terminal state so awaiting sessions don't outlive their parent. Two new execution-log event types — `auth-session-registered` (payload `{state, status: "awaiting"}`) and `auth-callback-received` (payload `{state, code: "***"}` on success or `{state, error, error_description}` on the ASPSP-reported-error variant, snake_case to match the rest of the event taxonomy) — join the closed taxonomy and are emitted into the parent run's execution log so a log consumer can reconstruct the full flow without scanning the run driver's own traces. Token exchange of the captured `code` (using `conformance.http`'s mTLS primitives) and an executor-side `awaitAuthorizationCode` step type are explicit follow-up PRs and are out of scope here.

- First-class `TestPlan` model with mandatory pre-population and explicit deselection (PRD Participant Story #4; OBL Standards Story #3). v1 manifest steps may now declare an optional `"optional": true|false` flag (default `false`) parsed strictly as a JSON boolean; `mandatory` and `optional` are mutually exclusive at parse time. The new `conformance.test_plan` module exposes `TestPlan` and `TestPlanEntry` dataclasses with `default_plan_from_manifest()` (selects every mandatory + non-optional step), `with_deselection()` (returns a new immutable plan with named step ids deselected — unknown ids raise `ValueError`), `selected_step_ids()`, `deselected_mandatory_step_ids()`, `is_eligible_by_selection()`, and `summary()`. The executor accepts a `plan` keyword on `run_manifest()`: deselected steps do **not** run and produce **no** `StepResult` (they are not the same as `SKIPPED`). When `plan` is omitted the engine builds the default plan from the manifest, preserving the previous behaviour exactly. The CLI gains a repeatable `--deselect STEP_ID` flag (manifest mode only — exits 2 if combined with no `--manifest` or if an id is unknown). The REST API accepts an optional `"deselectStepIds": [str, ...]` field on `POST /api/runs/`, validated against the inline manifest at request time (HTTP 400 on unknown ids or when supplied without an inline manifest). A new `step-deselected` event type joins the execution-log taxonomy and is emitted once per deselected step before any `step-started`, so a log consumer can read the plan-vs-manifest delta without scanning the entire run.
- Gated tier-2 Ozone headless PSU integration coverage runs only when both `OZONE_DISCOVERY_URL` and `OZONE_HEADLESS_PSU_SUPPORTED=true` are set; the workflow dispatch surface includes the opt-in flag and otherwise skips with the PRD open-investigation reason.
- Structured execution log written alongside every result file, exposed through `GET /api/runs/<id>/log/`, and masked by default with `CONFORMANCE_DEVELOPER_MODE=true` reserved for local debugging.
- Defence-in-depth loopback guard, bounded terminal-run history, REST API run surfaces, and `load_manifest_from_object()` support for local headless/CI usage.

### Changed

- `certificationEligibility` now includes an `approvedRelease` block in generated reports. Participant config can optionally supply `approvedReleasePolicyPath`; when the policy is absent or the current `tool.version` is not listed, the participant-side self-assessment is non-eligible while OBL-side validation remains authoritative and recomputes the decision from independent inputs.
- Mandatory `psu-authorization` steps are now covered by the same certification-eligibility accounting as HTTP steps. A mandatory PSU timeout is reported as `mandatoryFailed` (not `mandatorySkipped`), preserving the distinction between a conformance flow that ran and failed versus one that could not run due to a missing prerequisite.
- `certificationEligibility` gains two new fields, `mandatoryDeselected` (count) and `mandatoryDeselectedStepIds` (ordered list of step ids that were declared mandatory in the manifest but deselected from the plan). A new reason value `"Mandatory steps were deselected from the plan"` takes precedence over every other reason whenever `mandatoryDeselected > 0` — a mandatory step that never ran cannot demonstrate coverage, regardless of why. `mandatoryTotal` now counts both executed mandatory steps and deselected mandatory steps so the denominator stays consistent. The existing `"No mandatory steps declared"` reason is preserved for manifests that declare no mandatory steps at all.
- Result JSON now includes a top-level `plan` block sibling of `summary` (only when a `TestPlan` was supplied to the engine — smoke checks and v0 runs omit it): `{totalSteps, selectedSteps, deselectedSteps, mandatorySelected, mandatoryDeselected}`. Shape is stable and consumed by the upcoming HTMX plan-builder UI.
- API `create_run` now returns HTTP 400 for invalid JSON and invalid UTF-8 request bodies.
- Result-file request/response evidence, form bodies, WARN/SKIPPED outcome states, certification eligibility, and Ozone integration workflows are extended for the manifest-driven conformance flow.
- Manifest v1 and `send_json` support arbitrary HTTP methods, JSON/form request bodies, recursive placeholder resolution, and token-exchange examples.
- Pinned third-party GitHub Actions were bumped to Node 24-compatible releases, Google-style docstrings are enforced, and v0 follow-up/test-id handling was tightened.

### Fixed

- AIS account-resource assertions no longer require `Data.Account[*].Status`. The v4 Account and Transaction OpenAPI defines `Status` as an optional `OBAccount6` property while requiring only `AccountId`, so Ozone/model-bank account responses without account status now pass the baseline account checks; transaction `Status` checks remain because `OBTransaction6` requires them.
- Local dev server targets now serve HTTPS on port `8443` with a generated local certificate, so registered Ozone redirects to `https://0.0.0.0:8443/conformancesuite/callback` reach the callback endpoint instead of failing with `ERR_SSL_PROTOCOL_ERROR`.
- PSU callback handling now bridges OAuth hybrid fragment redirects by replaying browser-only `#code`/`state` or `#error` fields as a normal server-visible query callback while deliberately dropping `id_token`.

- Browser/API-launched conformance runs now write the structured result JSON and NDJSON execution log to the configured `resultOutputPath` and `executionLogPath`, matching CLI runs and making local `out/` artifacts available after guided E2E attempts.

- AIS certification baseline and slice suites now request the `accounts` scope on the client-credentials token used to create account-access consents, so Ozone model-bank consent setup receives a token authorised for `/account-access-consents` before PSU authorisation begins.

- `_blocking_reason_lines()` in the OBL certification validator now renders Confluence summary bullet lines in the same precedence order produced by `_validation_reasons()` (tool-version failures → mandatory-step failures → partial coverage), instead of always placing the `manifest_coverage_partial` bullet first. In multi-blocker scenarios this had hidden more actionable step/version failures beneath the lower-priority coverage message. Addresses Copilot PR #44 review feedback.

- `POST /api/runs/<run_id>/auth-sessions/` now explicitly rejects `multipart/form-data` requests that carry any parsed fields or files with HTTP 400, instead of silently treating them as bodyless. The previous "skip parsing for multipart" branch (added to accommodate Django's test client posting an empty multipart envelope for `client.post(url)` with no data) would have silently dropped a caller-supplied `state` posted as multipart form fields, reintroducing the silent-drop class of bug the parse-at-the-boundary change was meant to prevent. Empty multipart envelopes (no fields, no files) are still accepted as bodyless. Addresses Copilot PR #28 review feedback.
- `POST /api/runs/<run_id>/auth-sessions/` now re-fetches the run record after `auth_session_store.register(...)` and rolls back the just-created session via the new `AuthSessionStore.discard(run_id, state)` helper if the run has been pruned or reached a terminal state in the interim. Previously the active-run check ran before `register(...)` and `_execute_run`'s `discard_for_run` cleanup could fire between the two calls, leaving an orphaned `awaiting` session that outlived its parent run. The endpoint now returns 404 (run pruned) or 409 (run terminal) instead of 201 in that race; the happy-path response is unchanged.
- `run_manifest()` in `conformance/executor.py` now emits an `application-error` event (with `{"message": str(error)}`) before re-raising any unexpected exception that escapes the engine body after `run-started` has been emitted. Previously, an unhandled exception from `_run_manifest_v1` or `_run_manifest_v0` would leave the NDJSON log ending on `run-started` with no terminal event, breaking the log contract. Matches the fix applied to `run_model_bank_smoke_check` in PR #22.
- `RunStore.get_run_log_bytes()` now snapshots the `execution_logger` reference under the store lock and serialises the NDJSON buffer outside the lock. Previously the full `to_ndjson_bytes()` call (JSON-serialising every buffered event) ran while holding the store lock, unnecessarily blocking concurrent `status/result` updates and `create_run` calls for the duration of serialisation. `BufferedExecutionLogger` already protects its own buffer with a per-instance lock so snapshot-then-serialise is thread-safe.
- `config/settings.py` production guard no longer fires during tooling runs (`mypy`, `pytest`, `ruff`, `interrogate`, `pydoclint`, `coverage`). Previously, a developer with `DJANGO_SECRET_KEY=django-insecure-...` exported in their shell (the documented dev value) would see `mypy` crash with `Error constructing plugin instance of NewSemanalDjangoPlugin` because the Django plugin imports `config.settings` during construction and the guard refused to load. The guard still fires for `python`/`uvicorn`/`gunicorn` server invocations — the deployment safeguard is unchanged.
- `run_model_bank_smoke_check` now emits an `application-error` event (with `{"message": str(error)}`) before re-raising any unexpected exception that escapes the engine body after `run-started` has been emitted. Previously, an exception raised from `OzoneModelBankClient.from_config` (or any future unexpected engine bug) would leave the execution log ending with only `run-started`, breaking the log contract introduced in PR #22. The original exception still propagates unchanged so CLI and API error-handling is unaffected.
- `GET /api/runs/<id>/log/` now returns HTTP 500 (`{"error": "Execution log unavailable for this run"}`) when the run record exists but has no attached execution logger, rather than the incorrect HTTP 404 that was returned for both "unknown run" and "logger not attached". The 404 path (`"Run not found"`) is unchanged. The logger-absent path is an invariant violation in production code; 500 is appropriate.
- Defaulted model-bank smoke-check output, pre-commit secret scanning diff filters, the `config/settings.py` coverage omit comment, testing strategy docs, and `uv sync --no-install-project` usage.
